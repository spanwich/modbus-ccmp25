# CAmkES vs Bare-Metal Rootserver — Why Two Projects Make Opposite Choices

*Why `sel4_ccwmp25` (Path A) uses CAmkES, while `multikernel_qemu` (Path B) does not.*

## TL;DR — the premise correction

`build-sel4_ccwmp25/` **is** a CAmkES build. It is the output of the `sel4_ccwmp25`
project — **Path A**, the ICS cross-domain gateway. The directory is full of CAmkES
machinery: `camkes-gen.cmake`, `ast.pickle`, `camkes-tool/`, `ics_stm32mp25x.camkes.cpp`,
`std_connector.camkes.cpp`, and generated component dirs (`ics_inbound/`, `ics_outbound/`,
`wdt_kicker`, `camkes-putchar-client`).

The code that is **not** CAmkES is a *different* project: `projects/multikernel_qemu/` —
**Path B**, the multikernel-AMP MVP-Q scaffold. Its `settings.cmake` says so explicitly:

> `# Hand-rolled rootserver (no CAmkES, no capdl-loader).`
> — `projects/multikernel_qemu/settings.cmake:7`

So nothing "stopped using CAmkES." There are two projects making **deliberate, opposite**
framework choices because they solve different problems. This doc explains both choices.

## The two projects at a glance

| | **Path A — `sel4_ccwmp25`** (`build-sel4_ccwmp25/`) | **Path B — `multikernel_qemu`** |
|---|---|---|
| Framework | **CAmkES** | **Bare-metal rootserver** (no CAmkES, no capdl-loader) |
| Kernels | One seL4 kernel | Two independent kernels, one per A35 core |
| Boot driver | CAmkES assembly (`ics_stm32mp25x.camkes`) | Extended **elfloader** (PSCI `CPU_ON` per kernel) |
| Rootserver | Generated by CAmkES | Hand-rolled ~70-line C (`rootserver/main.c`) |
| Status | Working on HW + QEMU | Phase 1 design / scaffold |

## What CAmkES gives Path A

CAmkES (Component Architecture for microkernel-based Embedded Systems) is a **declarative
component framework** for a *single* seL4 kernel. You describe the system in an ADL
(`.camkes`) file, and the toolchain generates all the capability plumbing.

From `projects/sel4_ccwmp25/ics_stm32mp25x.camkes` (lines 26–109):

```camkes
component ICS_Inbound {
    control;
    dataport Buf(ICS_BUFFER_SIZE) in_dp;   /* 65536-byte shared buffer */
    consumes Notification in_ntfy;
    dataport Buf(ICS_BUFFER_SIZE) out_dp;
    emits    Notification out_ntfy;
}

assembly {
    composition {
        component WatchdogKicker wdt_kicker;
        component ICS_Inbound    ics_inbound;
        component ICS_Outbound   ics_outbound;

        connection seL4SharedData   inbound_to_outbound_dp(
            from ics_inbound.out_dp, to ics_outbound.in_dp);
        connection seL4Notification inbound_to_outbound_ntfy(
            from ics_inbound.out_ntfy, to ics_outbound.in_ntfy);
    }
    configuration {
        wdt_kicker.priority   = 50;
        ics_inbound.priority  = 150;
        ics_outbound.priority = 150;
    }
}
```

What you get **for free** from those ~80 lines:

- **Declarative architecture** — components, typed shared-memory `dataport`s,
  `Notification` endpoints, `connection`s, and per-component `priority`, all checked at
  build time.
- **Auto-generated glue** — capability setup, shared-frame mapping for dataports, IPC
  stubs, the capDL spec, and the root CNode layout. You never hand-write cap distribution.
- **Isolation by default** — each component is its own protection domain; a component can
  only touch caps the assembly granted it. Ideal for the gateway's `ICS_Inbound` /
  `ICS_Outbound` / `WatchdogKicker` separation.

The **cost** is build machinery. CAmkES needs a two-pass cmake build with an AST
generation step wedged in between:

> CAmkES requires two cmake passes with `ast.pickle.cmd` + `camkes-gen.cmake.cmd` between
> them: the first pass generates those scripts, running them produces the AST, and the
> second pass picks up the generated targets.
> — `projects/sel4_ccwmp25/CLAUDE.md` ("Build")

That cost is well worth it for Path A: one kernel, security-critical component separation,
a stable static architecture.

## What Path B does instead

Path B has no `.camkes` file at all. It declares an ordinary seL4 root task:

```cmake
# projects/multikernel_qemu/settings.cmake
set(KernelMaxNumNodes 1 CACHE STRING "" FORCE)   # verified unicore kernel
# "Verified unicore — each kernel runs on its own core. SMP fan-out is the
#  elfloader's job, not the kernel's."  (lines 36-38)
```

…and the rootserver is hand-written C using nothing but `sel4runtime` + debug syscalls:

```c
/* projects/multikernel_qemu/rootserver/main.c
 * Hand-rolled rootserver: prints "[K<id>] tick N" once per second forever.
 * No CAmkES, no capdl-loader. Just sel4runtime + libsel4 debug syscalls. */
int main(void) {
    put_str("[K"); put_dec(KERNEL_ID); put_str("] rootserver up\n");
    uint64_t tick = 0;
    while (1) {
        put_str("[K"); put_dec(KERNEL_ID); put_str("] tick ");
        put_dec(tick++); put_str("\n");
        busy_wait_seconds(1);
    }
}
```

No component framework, no ADL, no generated glue — ~70 lines total.

## Why the multikernel work drops CAmkES

The choice is not "CAmkES is bad." It is that **CAmkES does not address the multikernel
problem**, and it would add cost where there is no matching benefit:

1. **CAmkES is single-kernel by construction.** An assembly describes components *inside
   one* kernel image. Path B needs *two distinct kernel ELFs* with disjoint `/memory` DTS
   regions (e.g. `kernel_0` at `0x84000000`, `kernel_1` at `0x98000000`). You cannot
   express "two separate kernels on two cores" in a single CAmkES assembly.

2. **The hard part is *pre-kernel*.** Multikernel orchestration lives in the **elfloader**:
   load `kernel_0.elf` and `kernel_1.elf` to their physical addresses, then `PSCI CPU_ON`
   the second core at the second kernel's entry. CAmkES only runs *after* a kernel is
   alive, so it cannot help with the part that is actually novel. (See
   `docs/path_b_phase1_design.md`.)

3. **Build heaviness fights the goal.** Phase 1 is the smallest possible "two kernels boot
   and print to UART" demo. The design references explicitly cite *"a clever build system
   makes things harder"* (the Atoll lesson) as a reason to keep orchestration simple rather
   than fold it into a component framework. (See `docs/path_b_design_references.md`.)

4. **capdl-loader is overkill too — and deferred, not rejected.** Phase 1 hand-rolls the
   rootservers because capdl-loader is more per-kernel setup than a boot-and-print PoC
   needs. capDL / CAmkES are **deferred to Phase 2+**, where each kernel *could* run its own
   CAmkES-based system internally — that is a per-kernel concern, not a boot concern. (See
   the out-of-scope section of `docs/path_b_phase1_design.md`.)

## Trade-off summary

| Dimension | **CAmkES** (Path A) | **Bare-metal rootserver** (Path B) |
|---|---|---|
| Architecture | Declarative ADL, checked at build time | Imperative C; you describe nothing, you write everything |
| Cap distribution / glue | Generated (dataports, notifications, capDL, CNode) | Hand-written |
| Isolation | Strong defaults, per-component PDs | Whatever you build yourself |
| Build | Two-pass cmake + AST step | Plain single root task |
| Kernel scope | One kernel only | One kernel *per project*; multi-kernel via elfloader |
| Best when… | Security-critical component separation in one kernel | Bootstrap/coordination problems *below* the kernel |

The trade is: **CAmkES = declarative isolation + free glue, paid for with a single-kernel
assumption and a heavier build.** For Path A that is a clear win; for Path B it adds nothing
where the difficulty actually is, and gets in the way of a minimal bootstrap.

## When to use which

- **Use CAmkES** when the problem is *organizing components inside one kernel* with strong
  static isolation — exactly the ICS gateway (Path A).
- **Use a bare-metal rootserver** when the problem is *below the kernel* — booting and
  coordinating multiple kernels — where the elfloader, not a component framework, does the
  real work (Path B).
